# Campaign form: field parity with the approved design

Owner, 2026-11-17: the marketing portal's campaign ("Create coupon") form must
match the owner-approved design **field by field**. The design's field list is
[`ayman-draft-fields.csv`](./ayman-draft-fields.csv) (107 rows). This page maps
every row to the code as it was before the parity work
(`CAMPAIGN_FIELD_SPEC`, 83 fields, `packages/shared-types/src/marketing-engine.ts`
at `e5c9bd5`) and says what the v1 coupon does with it at issuance.

## Summary

|                                                                 | count                                              |
| --------------------------------------------------------------- | -------------------------------------------------- |
| Design rows                                                     | 107                                                |
| **same** - path unchanged                                       | 69                                                 |
| **renamed** - the code's path renamed to the design's           | 10                                                 |
| **missing** - added to the schema, the spec and the form        | 28                                                 |
| **extra-in-code** - removed                                     | 2 (`loyalty.reward`, `review.snapshot`)            |
| **extra-in-code** - kept, listed in `CAMPAIGN_CODE_ONLY_FIELDS` | 3 (`audience.match`, `audience.listId`, `studyId`) |

`CAMPAIGN_FIELD_SPEC` now holds exactly the 107 rows, in the design's order,
with its step, label, api*path, type, required and notes (a test pins it to
the CSV row by row). Each row's English label is `promo.field.<key>` in
`apps/marketing-portal/src/i18n/en.json`, its Arabic in `ar.json`; the key is
the path without `campaign.` and `[]`, dots as `*`.

## Old rows keep opening

Renamed paths are rewritten on read by `upgradeCampaignDraft`
(`readCampaignDraft` in `rowToCampaign`, `rowToStudy` and the sample engine's
browser store); `StoredCampaignDraft` accepts either shape on save, so a portal
deployed after the gateway still saves. Nothing is migrated in the database:
a row is rewritten in the new shape only when it is next saved.

| old path                                          | new path                                        | how an old row is read                                                                           |
| ------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `validity.startDate` / `endDate` / `daysOfWeek[]` | `schedule.*`                                    | moved as is                                                                                      |
| `validity.startTime` / `endTime`                  | `schedule.timeWindow.from` / `.to`              | moved; `schedule.allDay` = no time set                                                           |
| (none)                                            | `schedule.expiresAfterIssueDays`                | the old window's length in days (max 365), so an old campaign's coupons expire exactly as before |
| `offer.bxgy.productIds[]`                         | `offer.bxgy.productId`                          | the first id                                                                                     |
| `offer.deliveryFeeCovered`                        | `offer.deliveryFeeCoveredSar`                   | same value                                                                                       |
| `loyalty.stampsRequired`                          | `loyalty.type` STAMP + `loyalty.ordersRequired` | same number; a loyalty block with neither stamps nor milestones is dropped                       |
| `loyalty.reward`                                  | (removed)                                       | appended to `campaign.notes`                                                                     |
| (none)                                            | `scope.allBrands`                               | true when no brand was listed (the old "none = all")                                             |
| (none)                                            | `fraud.onePerPhoneAndDevice`                    | true for first-order / new-customer coupons (the design makes it mandatory)                      |

A row that no longer passes today's rules (for example PUSH with no message
copy) still opens: `readCampaignDraft` never refuses, and the engine checks
it when it is next saved.

## Rules added from the design's notes

Every required / conditional rule is one pure function, `campaignDraftIssues`
(shared by the form, the sample engine and the CRM's engine), behind
`CampaignDraft`'s `superRefine`; each issue carries a rule id the form
translates (`promo.rule.<id>`). Ranges and options are in the zod schema.

- Name: max 60, **unique** among campaigns not ended or rejected (engine: 409 `not_unique`).
- Compensation reason required for SERVICE_RECOVERY; partner share > 0 when a partner pays.
- Percentage 1-100; amount > 0; maximum discount mandatory for PERCENT and CASHBACK.
- BXGY needs its item; FREE_ITEM its item; a bundle at least 2 items, priced
  below their normal total (needs the menu: checked by the form and the sample
  engine; the CRM holds no menu).
- Partial redemption: FIXED only. A test (experiment): PERCENT / FIXED / CASHBACK only,
  version B required (1-100 on a percentage), split 10-90%.
- Bigger birthday gift: extra value > 0 when on. Loyalty: STAMP / CHALLENGE need
  orders (2-50), CHALLENGE a window, MILESTONE at least one order number;
  FREQUENT_ORDER needs a loyalty set-up.
- Audience: SEGMENT needs a condition, PHONES numbers (+9665XXXXXXXX), LIST a list;
  measurement group 0-20%.
- At least one payment method, order type, day and channel.
- All brands **or** a brand list; a monthly limit needs its maximum; a shared code
  its code (unique across campaigns that hold or will hold it); unique codes their count.
- Bank card ranges: 6-8 digit BIN or BIN-BIN of the same length, low to high.
- One per phone and device is mandatory for FIRST_ORDER, NEW_CUSTOMER and first-order-only coupons.
- Schedule: end on or after start; all day **or** a time window; both times or neither,
  different; expiry after issue 1-365 days; a flash offer needs its hours (1-168).
- Communication: PUSH needs title and message in both languages, IN_APP_BANNER its
  headline, SMS its text; consent must stay on for SMS and email (PDPL).
- Forecast inputs 0-100; when both are given they set the share who would have
  ordered anyway in the business case (`wouldOrderAnywayPct`).

## Locked when live

`LOCKED_WHEN_LIVE` now reads `schedule` (was `validity`) and adds `fraud`,
`communication` and `forecast`: once customers may hold the coupon, only the
name, notes, reason code and funding can change.

## Known gaps (not changed by this work)

- The design's note on `campaign.objective` says 15 objectives mapped to a
  catalogue C01-C25; the code has 16 objectives and no C-codes. The CSV gives no
  list, so the vocabulary is unchanged.
- `scope.categoryIds[]`: the design's note says "Value = BRAND|Category"; the
  form stores the catalogue's category id (brand-scoped, `brand:n` in the sample).
- `audience.excludeDiscountSensitive` (on by default) and `audience.visibility`
  are eligibility settings the v1 issuance does not apply and does not refuse -
  as before this work. Refusing them would block every existing campaign; a
  decision for the owner.
- Communication copy, send time, frequency cap, quiet hours and consent are
  stored and validated, but the v1 sender only attaches the coupon to the wallet
  and sends no message, so nothing applies them yet.
- The CRM's engine has no menu, so the bundle-price rule and the item pickers
  fall back to typed product ids there.
